*Case study · Eden AI*

# One way into the builder, three ways to start

Eden AI's workflow builder supported three starting behaviours: find a template, ask for AI assistance or begin from scratch. Tcules redesigned those paths around one adaptive entry surface, keeping search and AI modes distinct while connecting template discovery, previews, documentation access and workflow creation into one product task.

The work covered search and AI mode switching, template and feature discovery, preview cards, documentation access, node configuration, test feedback and keyboard use.

## At a glance {#case-context}

| Product | Eden AI's developer platform and its AI workflow builder, used by developers building with AI models. |
|---|---|
| Our role | Redesign of how people start a workflow: search and AI-mode interaction, previews and discovery. Eden AI looked after its own model providers, APIs, workflow engine and platform. |
| The key question | How can template search, AI help and a blank start share one entry point and still work as three different ways in? |
| What we delivered | One adaptive entry point linking search, AI assistance, templates and feature discovery to the workflow builder. |

Related Tcules services: [AI Search and Recommendation](/services/ai-product-ux/ai-search-recommendation) and [Product Design](/services/product-design).

## Three ways to start, and the cost of switching between them {#three-entry-points-created-three-versions-of-the}
A template helps a user recognise a known workflow. AI assistance can help express an intent that is not yet structured. Starting from scratch gives an experienced user direct control. Each mode is legitimate.

The problem was not their existence. It was the cost of moving between them. A user who entered through templates encountered a different discovery route from someone who started with AI or a blank workflow. Documentation and configuration context could become detached from the task.

Analytics and session evidence helped the team examine where discovery and creation were coming apart. The redesign needed to help people reach a working workflow from whichever starting point made sense to them.

## One search box that knows how you want to start {#search-became-a-shared-entry-not-a-single-undiff}

The design direction used one search component to recognise different kinds of intent. A user could search for a capability or template, move into an AI-assisted mode, preview relevant information and continue into the workflow builder.

Keyboard interaction made the mode change explicit. The design used Tab to move into AI assistance. That interaction allowed the interface to keep search and AI close without pretending they were the same operation.

## Previews preserved context before commitment {#previews-preserved-context-before-commitment}

Search results and templates need enough information to support selection. The redesign used preview cards and direct documentation access so a person could inspect a capability before adding it to a workflow. Progressive disclosure kept deeper technical material available without placing it all in the initial result.

Inside the builder, a horizontal workflow direction made the sequence of nodes visible. Configuration and test feedback stayed connected to the work being changed. The design goal was continuity: discovery, selection, configuration and testing should feel like states of one task rather than separate products.

## The builder became one connected task {#what-this-case-establishes}

The redesign connected the path from finding a capability to configuring and testing it. Tcules brought that continuity into the product by:

- recognising three valid creation modes;
- unifying their entry through adaptive search;
- keeping search and AI assistance distinct;
- connecting previews and documentation to selection;
- carrying chosen capabilities into node configuration; and
- returning test feedback to the workflow context.

Users could start with a known template, describe an idea or construct the workflow themselves, while staying within the same product experience.

## Use this when unifying entry points risks removing modes {#use-this-when-unifying-entry-points-risks-removi}

Unification should reduce unnecessary context changes without removing meaningful modes. A useful design test is:

1. Can the user start from recognition, description or construction?
2. Does each route preserve the same product objects?
3. Can the user inspect a capability before committing it?
4. Does feedback return to the state that caused it?
5. Are keyboard and assistive-technology interactions explicit?

When those answers are clear, a shared entry point can simplify the product without flattening expert work.

Designing shared entry points around search of this kind is the subject of Tcules' [AI search and recommendation](/services/ai-product-ux/ai-search-recommendation) work. Eden AI's CPTO discusses the product thinking behind this collaboration in [a Tcules podcast conversation](/insights/podcasts/do-ai-not-for-ai-s-sake-but-for-your-user-insights-from-eden-ai-s-ctpo).

## What the new model made easier to navigate {#delivery-impact}

| Impact dimension | What changed |
|---|---|
| Entry coherence | Three valid ways to begin a workflow were connected through one adaptive entry surface without pretending search and AI assistance were the same mode. |
| Task continuity | Discovery, preview, documentation, configuration and testing were connected as states of one product task. |
| Product extensibility | The entry model could recognise templates, features and described intent without creating a separate product path for each starting behaviour. |
