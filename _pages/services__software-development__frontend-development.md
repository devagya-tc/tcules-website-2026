*Software Development · Frontend development*

# Frontend development that matches the design on every screen

Long names, slow APIs, failed saves and the buttons each role should see: we build for what people actually meet, with tests and accessibility checks as we go.

[Start a conversation](#enquiry)

*Selected work: GT Tools · The Wandering Raven*

## When the frontend needs more hands or more care {#recognition}

**The designs are ready and nobody is free to build them.** Your engineers are busy with the backend, and the interface work keeps slipping.

**It works in the demo and breaks with real data.** Long names, empty lists, slow responses and expired sessions all appear at once.

**The design system lives mostly in Figma.** Components in production drift a little further from it with every release.

**Permissions show up as bugs.** People see buttons they cannot use, or miss the ones they can.

## Every state a user can meet {#states}

The design file shows the happy path. Your users will find the rest.

| Situation | What we build |
|---|---|
| **Waiting** | Loading states, background work that keeps the screen usable, progress for long tasks |
| **Nothing there yet** | Empty states that explain what to do first |
| **Something failed** | Clear error messages, saved input and a way to retry |
| **Different users** | Screens that change with roles and permissions |
| **Awkward content** | Long names, missing images, partial data and stale records |
| **Every screen size** | Layouts that work from a phone to a wide monitor |

These are part of the feature from the first commit, so nothing looks half-built when real data arrives.

## What our frontend work includes {#scope}

**Screens and components.** Built with your design system, or extending it through your team's contribution process.

**API connections.** Real responses, slow ones and failed ones, each with a message the user understands.

**Accessibility.** Keyboard use, focus order, labels and screen-reader behaviour, checked as we build.

**Performance.** Pages that load quickly and behave consistently across modern browsers.

**Tests and release.** Automated tests for key journeys, code review and release alongside your team.

## Frequently asked questions {#faq}

### What is the difference between frontend development and design engineering?

Design engineering uses code to settle how the product should look and behave. Frontend development builds the full interface for release: every screen, data connection, test and deployment step. Many projects use both; see [Design Engineering](/services/design-engineering).

### How do you check the build matches the design?

Our designers review the screens and their states against the design before release, and we fix any drift before customers see it. For a focused check on a product that is already live, see [Implementation QA](/services/design-engineering/implementation-qa).

### Can you work inside our existing frontend?

Yes. We learn your conventions, components, state handling, tests and release process first, so our code fits the application instead of starting a parallel one.
