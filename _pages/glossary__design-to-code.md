# Design to code

Design to code is the translation and continuing correspondence of product decisions from design representations into implemented software. When it matters: Correspondence becomes consequential at review and release, when a screen can look right while the behaviour beneath it has lost the decision it carried.

Design-to-code is also the boundary AI code generation must still cross.

Design-to-code includes semantic names, properties, states, content, responsive behaviour and accessibility. A role-specific action may appear correctly in a frame yet disappear in code without its explanation or recovery. That is a correspondence failure even when the screen looks similar.

Code generation can accelerate translation, but the result still needs product and technical acceptance. [Design intent](/glossary/design-intent) defines what must be preserved.

See [Design to Code](/services/design-engineering/design-to-code) or inspect an existing implementation through the [Design-to-Code Audit](/audits/design-to-code-audit).

## How is design-to-code used in practice? {#practice}

Design-to-code work is useful when the main risk is not creating the design but preserving an approved product decision during implementation. The team traces important states, content, responsive behaviour, permissions and recovery from the design reference into the running interface. Differences are then classified as implementation defects, outdated design references or intentional changes that need a product decision.

Tcules applies this through [Design-to-Code](/services/design-engineering/design-to-code) and the [Design-to-Code Audit](/audits/design-to-code-audit).

## How does design-to-code differ from frontend development? {#comparison}

The table separates a fidelity and decision-preservation problem from broader frontend delivery.

| Design-to-code | Frontend development |
|---|---|
| Starts with an approved product or interaction reference | Starts with an agreed software scope and product behaviour |
| Focuses on whether intent survives implementation | Covers the wider running frontend, architecture and release work in scope |
| Can end with corrected reference code or QA findings | Produces maintained application code where production delivery is included |
