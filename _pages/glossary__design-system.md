*Glossary · Design System*

# Design system

A design system is shared product infrastructure made of foundations, reusable components and patterns, design assets, coded implementation, guidance and an operating model for change. When it matters: The term earns precision when an organisation must decide what is genuinely shared infrastructure and what is one product's local choice.

The boundary between shared infrastructure and a local product choice matters more than the component count.

A component library is one representation of a design system. A shared status decision, for example, must carry the same meaning through foundations, Figma, code, documentation, release and a consuming product. The system also needs ownership, contribution and migration.

[Design-system governance](/glossary/design-system-governance) explains how shared decisions change. [Design-system adoption](/glossary/design-system-adoption) asks whether product teams use them, while [design-system drift](/glossary/design-system-drift) names unintended divergence.

Explore the [Design Systems](/services/design-systems). The [public Matter design-system reference](/matter-design-system) demonstrates a bounded design artefact, not organisational adoption or governance.

## How is a design system used in practice? {#practice}

A design system becomes useful when several products or teams repeatedly make the same interface decision. The shared layer should carry the parts that genuinely need one answer, while product-specific behaviour can remain local. In the [Auxentios case](/case-studies/auxentios-cpq-product-mvp-design), Tcules developed components, tokens and layout guidance from the product model rather than treating the library as a separate exercise.

The open-source [Matter design system](/matter-design-system) provides a public Tcules design artefact that can be inspected directly.

## How does a design system differ from a component library? {#comparison}

The table separates reusable interface assets from the wider system needed to keep shared decisions coherent.

| Component library | Design system |
|---|---|
| Reusable interface components | Foundations, components, patterns, design assets, coded implementation, guidance and an operating model |
| Answers how a shared element is represented | Also answers what belongs in the shared layer, how it changes and how products adopt it |
| Can exist without a contribution or migration model | Requires ownership and a route from change to consuming products |

## Why design system matters in product work {#next}

What the shared system should own, and what should stay local to a product, is the decision behind the definition.
