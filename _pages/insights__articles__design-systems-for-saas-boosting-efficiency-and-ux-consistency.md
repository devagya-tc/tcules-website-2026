# How to build a SaaS design system product teams keep using

By [Shoghi Bagul](/insights/authors/shoghi-bagul) · Published 2 May 2025 · Updated 26 October 2026 · 9 min read

This article explains what makes a SaaS design system work after the library exists. It covers how teams change the system and what has to stay in step across design, code and documentation. It also covers how big the system should be for your product, and what to measure.

Start with one test. A product team needs a version of a component the library does not cover, such as an error or loading view. Can the team contribute the change, get a decision and use the result in its release? Or does it create another local version? What happens next shows how well the system works.

Foundations, components and documentation matter. So does the route by which teams change and adopt them.

**Key takeaways**

- A design system works when the quickest way for a team to ship is also the way that keeps the design as intended.
- Meaning, behaviour, releases and the reasons behind each pattern need to match across design, code and documentation.
- Treat the people who use the system as real users, with contribution routes, real examples and migration support.
- Size the system to the repeated cost and the number of teams it reaches. A small team may need only foundations and core components.
- Measure reuse, overrides, divergence and contribution lead time alongside coverage, which alone can reward an unused library.

## Design system adoption in SaaS: why a polished library goes unused {#the-library-is-not-the-outcome}

Reuse, consistency and efficiency depend on how teams use the components once they exist. A team may have a polished library and still see:

- engineers rebuilding components because coded versions are missing or unreliable;
- designers detaching components to meet real requirements;
- accessibility behaviour documented but not tested in production;
- product-specific patterns that cannot enter the shared system;
- releases that arrive without migration guidance;
- unclear ownership when a token (a named design value, such as a colour) or a component changes.

The system is working when the quickest way for a team to ship is also the way that keeps the design as intended.

## What should a SaaS design system include? {#what-should-a-saas-design-system-include}

A SaaS design system is the shared set of design values, components, patterns and rules that lets several people build one product so it looks and behaves as one. Its parts arrive in roughly this order:

| Part | What it holds | When you need it |
|---|---|---|
| **Foundations** | Colour, type, spacing and other values, named for their purpose | From the first screen |
| **Components** | Buttons, fields, tables and dialogs, each with its states: empty, loading, error, disabled | As soon as two people build screens |
| **Patterns** | Repeated product situations, such as filtering a list or approving a record | When the same situation appears in several places |
| **Guidance** | Why each pattern exists, where it applies and when to extend it | When people outside the core team use the system |
| **Contribution and release** | How a new need gets in, who decides, versions and migration notes | When more than one team depends on it |
| **A coded package** | The components as maintained code that products install | When engineers would otherwise rebuild them |

UX consistency is the visible result. The parts underneath are what keep it from wearing away with each release.

## How SaaS teams keep Figma, code and documentation aligned {#four-things-must-correspond-across-design-code-a}

Four things need to match.

### Meaning: do names say the same thing everywhere? {#semantic-correspondence-keeps-the-same-meaning-across-representations}

Names should mean the same across design, code and documentation. A token called `surface-danger` communicates purpose. `red-500` communicates implementation. The [Design Tokens Community Group specification](https://www.designtokens.org/tr/drafts/format/) provides a vendor-neutral format for exchanging token information. Each product still needs its own semantic model.

### Behaviour: do components act the same in design and in the product? {#behavioural-correspondence-keeps-states-and-interactions-aligned}

Component states, validation, keyboard behaviour, loading and error handling should match between the design references and the running software.

### Release: does what shipped match what was designed? {#release-correspondence-checks-what-actually-reached-the-product}

Design assets, packages, documentation and migration notes should refer to compatible versions. Teams can see what changed and who is affected.

### Decisions: can people see why a pattern exists? {#decision-correspondence-keeps-product-intent-visible-through-implementation}

The system records why a pattern exists, where it applies, and when a product team should extend it or use it as it stands.

Figma's [Code Connect documentation](https://help.figma.com/hc/en-us/articles/23920389749655-Code-Connect) illustrates one way to link design components to implementation snippets. The link is useful, and product-specific behaviour still needs its own review.

## Treat the teams using the system as its customers {#adoption-is-a-product-problem}

Treat the people who use the system as real users: product designers, engineers, content designers, QA and sometimes external teams. They have jobs, constraints and switching costs.

Tcules applies this view through [Design Systems](/services/design-systems). When the cause of drift is unclear, begin with the [Design System Audit](/audits/design-system-audit).

Adoption improves when the system offers:

- a faster route to a dependable result;
- clear boundaries between foundation, component and product pattern;
- examples drawn from actual product situations;
- responsive and accessibility behaviour as well as appearance;
- contribution criteria proportionate to the change;
- maintainers with visible decision authority;
- release communication and migration support.

The [GOV.UK Design System contribution criteria](https://design-system.service.gov.uk/community/propose-a-component-or-pattern/) are useful because they ask for evidence of need and community work before a pattern becomes shared.

## A design system for SaaS startups and scale-ups: sizing it {#not-every-product-needs-a-programme}

A small team with one product may need only its core design values, a focused component set and explicit conventions. A formal contribution council, a detailed taxonomy and a separate documentation platform can wait until more teams depend on the system.

Invest in line with repeated cost and the number of teams the system reaches.

| Product situation | Appropriate system response |
|---|---|
| One product, small team, early change | Foundations, core components and lightweight decisions |
| Several squads on one platform | Shared code, release discipline and pattern ownership |
| Product family or white-label platform | Shared design values with agreed meanings, plus contribution and migration routes |
| Regulated or high-consequence workflows | Tested behaviour, accessibility evidence and stricter change control |

## SaaS design system examples worth studying {#saas-design-system-examples}

Public systems from large SaaS companies are the easiest examples to learn from. Shopify Polaris, Atlassian's design system, Salesforce's Lightning Design System and GitHub's Primer are all published openly. Read them for how they explain intent, states and contribution, beyond the catalogue of components.

Their scale suits platforms with many teams and outside developers. Take the habits, and size your own system to the teams it serves.

For a Figma design system example you can take apart, [Matter](https://www.figma.com/community/file/1314109325852179933/matter-design-system-free) is our own, published free on Figma Community. It shows how we name colour, spacing and type values and assemble components from smaller parts.

## Design system lessons from our work with Doodle and Gold Image Printing {#design-system-lessons-from-our-work}

Two projects show the same route from opposite ends.

On [Doodle](/case-studies/doodle-case-study-automating-enterprise-meeting-scheduling), the product already had a design system. Standard interactions in the new enterprise scheduling direction used existing Doodle components. The calendar and bookability work needed new ones, which we organised to stay consistent with the product system. That is the contribution route below in practice: check the system first, and add only where the product need is new.

On [Gold Image Printing](/case-studies/gold-image-printing-web-to-print-erp-modernisation), there was no shared foundation to join. We designed the components first, then used them across the web-to-print store and the internal ERP, with one style guide for both. A repeated interaction could be discussed with engineering once, then applied wherever it fitted. Customers and production staff could move between the two surfaces and still recognise the product.

## How changes get into a design system, in five steps {#how-a-product-need-becomes-a-shared-release}

The route has five steps:

1. A product need first checks the current system.
2. A real gap enters contribution and review.
3. Approved work updates design, code and guidance together before release.
4. The release record keeps the owner, version, affected products, accessibility acceptance and migration requirement visible.
5. Adoption and observed issues feed the next revision.

[Design System Implementation](/services/design-systems/design-system-implementation) is the route when step 3 must produce a maintained code package that real products use.

The [Design System Drift Checker](/tools/design-system-drift-checker) traces one component family through design, code and real use. It can show whether adoption is the problem or a symptom.

## Design system ROI for SaaS: what to measure besides coverage {#what-to-measure}

Coverage alone can reward a large unused library. Combine it with:

- reuse in design and production;
- detached or overridden instances;
- time to implement a supported pattern;
- implementation divergence;
- defects traced to shared components;
- contribution lead time;
- migration completion;
- accessibility acceptance;
- product-team confidence in when to reuse or extend.

A system earns its investment when it makes product work cheaper and more dependable for the teams that use it. That is the centre of Tcules' [Design Systems](/services/design-systems) work and the reason [Design Engineering](/services/design-engineering) belongs beside it.

## What a shared component must prove before release {#what-must-a-shared-component-prove-before-releas}

Before accepting a contribution, name who will maintain it, which products and states it supports, how compatibility will be checked and how consumers will migrate. Count a component as adopted when teams use it for common states without rebuilding it or working around it. An installed package shows only that it arrived.

A practical release check combines rendered states, interaction behaviour, accessibility checks and visual comparison. Automated checks catch only part of the risk, so representative product contexts and human review still matter.

A pattern can stay local when its meaning or constraints belong to one product.

The release check is about to gain a second audience. AI coding tools already generate interface code from whatever a design system documents, and they follow names, states and usage rules literally. A component whose rules are written down clearly enough for a machine to apply is one that generated work will reuse instead of copying. The SaaS teams that write their systems for both readers will ship AI-assisted features that still look and behave like one product.

## SaaS design system FAQs {#faq}

### What should a SaaS design system include?

Foundations named for their purpose, components with all their states and patterns for situations your product repeats. Add guidance on why each pattern exists, a contribution route and release notes with migration help. A maintained code package follows once more than one team ships with it.

### Which SaaS design systems are good examples?

Shopify Polaris, Atlassian's design system, Salesforce's Lightning Design System and GitHub's Primer are public and worth studying. Read them for how they document intent and contribution as well as components. Their scale suits large platforms, so borrow the habits and size the system to your own teams.

### How do SaaS teams keep Figma and code aligned?

Agree which source governs each kind of design choice, name tokens for meaning in both places and sync them with a pipeline instead of by hand. Link Figma components to their code, for example with Code Connect. Then check behaviour, states and releases as well as appearance.

### How do changes get into a design system?

A product need first checks the current system. A real gap goes through contribution and review, then design, code and guidance change together and ship with an owner, a version and a migration note. Adoption and reported issues feed the next revision.

### Is a design system worth it for a SaaS startup?

Usually, in a small form: foundations, a focused set of core components and explicit conventions. A contribution council, a detailed taxonomy and a separate documentation site can wait until several teams depend on the system. Invest in line with the repeated cost and the number of teams it reaches.
