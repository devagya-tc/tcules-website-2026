Tcules design system

Making a component

Everything from an empty machine to a merged pull request. Every command says where to run it, and anything that can be handed to Claude Code is written out as a prompt you can paste.

Once, on a new machine

Getting set up

Four things, and you only need the first from a person: ask the repo owner for a collaborator invite on devagya-tc/tcules-website-2026 and accept it from your email or github.com/notifications. The repo is private, so a clone fails until you do — and it fails with a confusing “repository not found” rather than “no access”.

Ask for one more thing at the same time: access to the Tcules project in Claude Design. That is where the ten live components live and where you will write every spec — a repo clone does not give it to you, and it is the other half of this workflow.

Then install these three, if you do not have them:

  • Node 20.11.1 or newer — nodejs.org
  • GitHub CLI — cli.github.com, or brew install gh
  • Claude Code — this is where you will spend most of the time

Open Terminal (macOS: ⌘ Space, type “Terminal”. Windows: use Git Bash or WSL). Start Claude Code by typing claude and pressing return. Then paste the prompt below. It clones the repo, installs it, proves it works, and explains it to you — and it will ask you where to put it rather than choosing for you.

Where “the repo folder” means, from now on

Whatever path you chose in step 1 — ~/dev/tcules-website-2026 if you took the suggestion. Every command in this guide labelled in the repo folder runs there. To get back to it in a new Terminal:

Terminal · anywhere 
cd ~/dev/tcules-website-2026

Then start Claude Code with claude. It picks up the folder you are standing in, which is why the folder matters more than anything else on this page.

Every time, before you touch anything

Get current, then branch

Two rules, and they exist because nothing on the server enforces them. A branch protection rule for main does now exist in the repository settings, but GitHub does not honour one on a private repository on this plan — that needs a Team or Enterprise organization account. So the rule records the intent and a direct push still sails straight through it. What actually keeps main clean is that people do this:

  • Never commit to main. Always work on a branch.
  • Always start the branch from an up-to-date main, or you will be resolving conflicts that did not need to exist.
Terminal · in the repo folder 
git checkout main
git pull
git checkout -b feat/accordion

One thing does push back. npm ci installs a pre-push hook that refuses any push landing on main, whatever the branch you are standing on is called. If it fires, you meant to be on a branch and are not — the message it prints tells you how to move the commits across. It is a guardrail and not a gate: it lives in your own checkout, so it cannot help a machine that never ran an install, and git push --no-verify steps around it on purpose.

Branch names follow what is already in the repo: feat/ for something new, chore/ for tooling and housekeeping, then a short lowercase-hyphenated name — feat/site-header-footer, chore/design-sync. One branch per component.

Or hand the whole thing over:

Phase one

Decide whether you need a new component at all

Browser · claude.ai/design 
Open the Tcules project — the one whose component list is:
Section · Layout · Cluster · Button · Icon · Logo · Prose
SiteNav · SiteFooter · Breadcrumbs

That is the project the owner shared with you during setup. If you cannot see it, you have not been added — ask, rather than starting a new project, because a fresh one has no component library in it and everything below silently stops working. Those ten are the real shipped components, not pictures of them.

Everything in phase two happens in that project. Not a normal Claude conversation, not a new design project — the library is what makes the mockup real and the spec short.

For the eighteen components the content audit identified, this question has already been asked. docs/briefs/README.md records the answer, component by component — and for four of them, Button, Prose, SiteNav and SiteFooter, the answer is that shipped code already covers it. Those four briefs say do not specify this and list what to verify instead. If yours is one of them, phase two is not your next step; reading the brief is.

The only question that matters yet

Can this be built from those ten and the props they already have?

Before deciding it is new, check the cheaper answers: a new emphasis, tone or size on Button; a glyph in the icon set; a surface or density on Section; a columns / rowGap / colGap arrangement in Layout or Cluster; a rule inside Prose; a prop or slot on an existing pattern.

Yes — it exists

Compose it

You are finished when the mockup is. No spec, no build, no branch, no pull request. Every component in it is the real one, so its four surfaces, its states and its props are correct by construction. Hand over the mockup and which props you used.

No — it is genuinely new

Specify it

Everything below. Reaching “nothing new is needed” is the more valuable outcome: the previous codebase reached the opposite conclusion 111 times, and that is the reason this one exists.

Phase two · in Claude Design

Write the spec

  1. 01

    Open the brief for your component

    Repo folder · any editor 
    docs/briefs/<NN>-<component>.md

    Select all of it. That is the whole step. There is one of these for each component the content audit identified, and it is already written: what the thing is, which pages carry it and how many, the closest existing component, the constraints that come from real content, and what is being left to your judgement. Nothing to fill in and nothing to combine.

    Read docs/briefs/README.md first. It gives the order to run them in, names the four that already ship — Button, Prose, SiteNav, SiteFooter — so you do not specify something that exists, and flags the three carrying a decision that is not yours to make. Those three say so inside the brief itself, marked UNRESOLVED, so the question travels with the document instead of being guessed at.

    Specifying something that is not one of the eighteen? Then there is no prepared brief, and you generate one:

    Terminal · in the repo folder 
    npm run design:brief | pbcopy

    That prints the same document with the seven fields blank, for you to fill in: component name, what it is in one sentence, where it appears, the closest thing that already exists, references, hard constraints, and what you are leaving to Claude's judgement. The fourth field saves the most time — and it is the one that most often sends you back to phase one.

  2. 02

    Know where the token names come from

    You will not find the colour ramps inside the brief any more. Every colour with its hex values, the nine spacing steps, all 19 type roles and which 12 carry a letter-spacing companion, the glyph set, the prefixes already taken, each existing component's measurements and the three layout primitives' real props live in vocabulary.md, a guidelines document in the Tcules project. It is generated out of the repo's token layer, so a name in it is a name that resolves in the browser.

    One copy in the project rather than a copy inside every brief — but the staleness rule is unchanged and it is the whole reason any of this is generated: a hand-kept list of token names is right for about a week and then starts lying. If a token is renamed in the repo, that document has to be regenerated and pushed to the project again — nothing checks it for you, so if a name in it looks wrong, say so rather than working around it.

    If you cannot see it in the project, stop and say so rather than working from memory of a similar system. A plausible-but-wrong token name renders perfectly and is wrong forever, and no build check can catch it.

  3. 03

    Paste it into the Tcules project and send

    Browser · claude.ai/design · the Tcules project 
    Paste the brief you just opened, whole.

    The project matters more than the prompt. With the library loaded, the mockup gets composed from real components and the spec covers only the genuinely new part. Send the same text in a plain Claude conversation and you get a spec that re-describes Section back at you, plus an implementer who has to work out which half is new.

  4. 04

    Read what comes back

    An eighteen-section spec ending in a self-audit with real counts. Two things to check yourself:

    § 6, per-surface colour. One row per token and four full columns — paper, tint, ink, blue — with a measured contrast ratio in every cell that is an accessibility floor. No cell saying “same as paper”. That repetition is the design work: a colour means different things on different grounds, and a table carrying only the differences has already caused a measured 1.13:1 failure here.

    § 17, open questions. Each marked BLOCKING or non-blocking.

Phase three · back in the repo

Land the spec

  1. 05

    Save it into the repo

    Copy the whole spec out of Claude Design, then paste this into Claude Code with the spec after it:

    Prompt 3 · save the spec

    Claude Code · in the repo folder

    Save the spec below to docs/specs/Accordion.md exactly as written — do not edit,
summarise or reformat it. Then check it against docs/component-spec-template.md and tell
me which of the eighteen sections are missing or empty, and list every open question
marked BLOCKING. Do not start building.

--- spec follows ---
<paste the spec here>

    The spec is the seam between design and code, and it needs a git history because the why comments in the finished CSS come from it. Without one, the next person re-argues every decision.

  2. 06

    Get the blocking questions answered

    needs the owner

    This is one of the few things you cannot do alone. A BLOCKING question is almost always “which existing thing must this line up with”, and the answer changes what gets built. Send the owner the list Claude Code just gave you.

    When the answers come back, write them into the spec and change Status: draft to Status: accepted. The build command refuses to start on a draft, on purpose: a spec with an unanswered blocking question produces a component built on a guess.

  3. 07

    Commit the spec on its own

    Terminal · in the repo folder 
    git add docs/specs/Accordion.md
git commit -m "Add the Accordion spec"

    A separate commit from the code, so a reviewer can read what was agreed before reading what was built.

Phase four · in Claude Code

Build it

  1. 08

    Run the build command

    Claude Code · in the repo folder 
    /build-from-spec docs/specs/Accordion.md

    It works through gates in order and writes the five files a component needs, plus the three it has to edit. You do not need to know which — but you do need to answer it.

  2. 09

    Expect it to stop, and answer honestly

    Stopping is the feature. In testing it correctly stopped on a spacing value that was not one of the nine steps, a colour with no ramp behind it, a state whose styling could not reach the part it moved, and — twice — a spec asking a component to import its siblings.

    If it asks something you cannot answer, that is a real question for the owner, not a reason to guess. Waving a gate through is how a wrong value gets built and then copied.

Phase five

Check it

  1. 10

    Run the checks

    Terminal · in the repo folder 
    npm run verify

    Six checks. They must all pass before you open a pull request. If one fails, the message names the file and the line — paste the whole thing into Claude Code and ask it to fix the cause rather than silence the check.

    Claude Code · in the repo folder 
    /audit-component Accordion

    An independent read-only pass that reports and does not fix. It catches things no script can: a margin where the container should own the gap, a hand-rolled layout, a restated font size.

    Terminal · only if the component is interactive 
    npm run build && npm run aria:check

    Proves every screen-reader reference in the rendered page points at something that actually exists. It needs a build, which is why it is not in verify.

  2. 11

    Look at it

    only you can do this
    Terminal · in the repo folder 
    npm run dev

    Open the URL it prints, go to /design/accordion, and on each of the four surfaces: hover it, hold the mouse button down on it, and tab to it with the keyboard.

    Those three states have no props by design, so no screenshot and no script can check them. This is the one step nothing in the pipeline can do for you — a green verify is not a substitute for having looked. Stop the server with Ctrl-C.

Phase six

Ship it

  1. 12

    Commit, push, and open a pull request

    Hand it over — this is the step most worth not doing by hand:

    Prompt 4 · open the pull request

    Claude Code · in the repo folder

    Ship this branch. In order: run `npm run verify` and stop if anything fails; show me
`git status` and `git diff --stat` so I can see exactly what is about to be committed;
commit the work in focused commits with messages in this repo's style (read the last few
with `git log` first); push the branch; then open a pull request into main with `gh pr
create`, whose body says what the component is, which spec it implements, the checks you
ran with their real output, and anything you had to decide that the spec did not cover.
Give me the PR link. Do not merge it.

    Pushing the branch is safe — it cannot affect anyone else's work. Opening the pull request is what asks for review.

  2. 13

    Watch the checks, then get it reviewed

    A GitHub Action runs npm run verify on the pull request, so the six checks get confirmed by a machine and not by your memory. If it goes red, fix it on the same branch and push again — the pull request updates itself.

    Terminal · in the repo folder 
    gh pr checks
gh pr view --web

    Then ask the owner to review it. Merging is theirs; nothing else on this page is.

  3. 14

    The owner merges it

    not you

    Review and merge are the owner's. What they do is squash the branch into one commit on main and delete the branch — the same shape as the pull request that brought the header and footer in.

    Terminal · the owner, in the repo folder 
    gh pr merge <number> --squash --delete-branch

    If they ask for changes instead, make them on the same branch and push again. The pull request updates itself and CI re-runs; never open a second one for the same work.

  4. 15

    Clean up, and get current again

    Terminal · in the repo folder 
    git checkout main
git pull
git branch -d feat/accordion

    Do this before starting the next thing, not after. Branching from a stale main is how you end up resolving conflicts that did not need to exist.

Phase seven · the owner's half

Getting the new component back into Claude Design

Merging does not put your component in the design library. Until someone re-syncs, that project still holds ten components — so the next person to want an accordion will write another spec for the one you just built. This is the step that closes the loop, and it is worth understanding even though you do not run it.

Why you cannot run it

The sync toolchain lives in .ds-sync/ and its build output in ds-bundle/, and both are gitignored — they are deliberately not in the repo, so a clone does not include them. The re-sync also is not a single command: its own driver describes a chain of build, diff, validate and capture, after which an agent grades the rendered preview sheets and does an attended upload. It needs judgement, not just a keystroke.

Guidelines are the exception. The vocabulary document is a plain file in the project, not part of the bundle — so updating it needs neither .ds-sync/ nor a graded preview, only write access to the project. That is what let the token names move out of every brief without waiting for a component re-sync.

What the owner does, so you know what to ask for:

  • Runs the re-sync driver, which rebuilds the bundle and the type declarations, diffs against what the project already has, and captures preview cards only for what actually changed.
  • Reviews the new component's preview sheet, and any warning the validator raises that is not already recorded in .design-sync/NOTES.md as known.
  • Authors a preview for the new component — one per component, hand-written, so the card shows the states worth seeing rather than a default render.
  • Uploads, at which point the library has eleven components and composition can answer what used to need a spec.

If your build added a glyph, say so in the pull request

The icon set is enumerated by hand in two places inside .design-sync/ — a type union and a preview array — and both feed the library. npm run design:check now fails if they drift from glyphs.ts, so the pull request will catch it, but the owner needs to know a re-sync is due for the icon card as well as the new component.

Batching is fine; forgetting is not

Nothing breaks if several components merge before one re-sync — the diff stage only captures what changed, so a batch costs little more than a single. What costs real time is a library that has quietly fallen a few components behind, because every request it cannot answer turns into a spec that did not need writing.

The short list

When you genuinely need the owner

Five things, and everything else on this page you can do alone.

  • The collaborator invite, and access to the Tcules project in Claude Design. Both once, at setup. The second is the one people forget to ask for.
  • Answering a BLOCKING question in a spec, and changing its status to accepted.
  • A new token, a new spacing step, or a new colour. These change the system for every component, not just yours — the build command stops and asks for exactly this reason.
  • Reviewing and merging the pull request.
  • Re-syncing the design library afterwards, for a new component, so yours becomes something the next person can compose with instead of re-specify. The tooling for it is not in the repo — see phase seven. A guidelines change is different and is not on this list: pushing an updated vocabulary.md needs no bundle and no preview grading, only write access to the project.

If something else has you stuck

Paste the error into Claude Code and ask it to explain the cause before fixing anything. The checks in this repo are written to name the file, the line and the rule — they are meant to be readable by whoever hit them, not just by whoever wrote them.

One thing the library cannot show you

Only still states are in it. SiteNav's open menu and mobile drawer, and every hover, press and focus state across all ten components, need interaction and appear in no card. If your design depends on one of those, say so in the spec rather than assuming the card showed you everything.
